# EDA Findings — sql-analytics-case-study

**Дата:** 2026-10-13
**Полный отчёт:** `reports/eda/eda-sql-analytics-2026-10-13.md`

## Датасет вкратце

`sql-analytics-case-study` содержит 7 таблиц: синтетический продуктовый трек
(20 000 `users`, 182 892 `events`, 928 `orders`, 268 `subscriptions`, 53 `refunds`,
98 `subscription_cancellations`, seed 42) и реальный трек UCI Online Retail II
(1 067 371 invoice line, 2009-12 → 2011-12). Период синтетики: 2024-01 → 2024-06.
Качество синтетики — **хорошее** (0 дублей, 0 пропусков, 0 будущих дат); реальный
трек — **приемлемое** (полные дубли строк 3.2%, null `customer_id` 22.8%,
экстремальные выбросы `price`/`quantity`). Главная проблема — не в данных, а в
**нарративе README**: 54% приписаны не тому шагу воронки, A/B treatment занижен.

## Топ проблем качества

### Проблема 1: README приписывает «54%» не тому шагу воронки
- **Что:** `README.md:3,41,58` — «funnel drops **54%** at cart→checkout».
  Фактический провал cart→checkout = **77.8%**; 54.9% — это view_item→add_to_cart.
- **Влияние:** портфолио-инвариант «правда → глубина → нарратив» нарушен —
  headline-число и его подпись расходятся; интервьюер поймает на первом же прогоне.
- **Действие:** переписать headline на «78% на cart→checkout; 54% — view→cart»,
  добавить инвариант-тест «headline step == argmax(step_drop)».
- **Владелец:** аналитик (автор портфолио)

### Проблема 2: A/B treatment в README занижен (4.9% вместо 5.18%)
- **Что:** `README.md:44,237` — «4.9% vs 3.8% (+1.1pp)»; данные дают
  control 3.77% / treatment **5.18%** / +1.41pp, z=4.81 (p≈2e-6). `cases.md` (case 09)
  уже корректен.
- **Влияние:** заниженный lift искажает интервью-тезис о силе A/B-сигнала;
  рассинхрон README ↔ cases.md ломает «два источника истины».
- **Действие:** привести README к cases.md: «5.2% vs 3.8%, +1.4pp».
- **Владелец:** аналитик

### Проблема 3: полные дубли строк в реальных данных (3.2%)
- **Что:** `online_retail.parquet` — 34 337 полных дублей строк (32 909 групп),
  порог FAIL >1% превышен.
- **Влияние:** если бы case 26 считал позиции без сворачивания до счёта, выручка
  была бы завышена; сейчас сворачивание `GROUP BY customer_id, invoice` делает
  дубли безвредными — но это неявная зависимость.
- **Действие:** принять риск явно (в отчёте и в `data/realdata/README.md`),
  подтвердить, что все потребители таблицы агрегируют до счёта/клиента.
- **Владелец:** дата-инженер

### Проблема 4: null `customer_id` (22.8%) и экстремальные выбросы price/quantity
- **Что:** 243 007 строк без `customer_id` (гостевые); `price` min −53 594,
  `quantity` ±80 995 (корректировки / bad-debt / ручные записи).
- **Влияние:** без фильтров `customer_id IS NOT NULL`, `price > 0`, `quantity > 0`
  любая агрегация по клиенту/выручке смещена или взорвана.
- **Действие:** оставить фильтры case 26 как обязательный контракт; задокументировать
  семантику отрицательных значений.
- **Владелец:** дата-инженер

### Проблема 5: «top 15% = 65%» неоднозначна
- **Что:** `README.md:45,153,228` — «top 15% = 65% of revenue». Это верно для bucket
  «11+ заказов» (14.9% клиентов → 65.2% выручки), но top-15% **по выручке** = 71.6%.
- **Влияние:** читатель может сверить с «top decile = 63.9%» и решить, что цифры
  противоречат друг другу.
- **Действие:** уточнить формулировку: «14.9% клиентов с 11+ заказами дают 65%
  выручки»; top-10% по выручке = 63.9%.
- **Владелец:** аналитик

## Что в порядке

- Синтетический трек — 0 полных дублей, 0 пропусков, 0 константных колонок, 0 будущих дат.
- FK целостность: 0 сирот `events.user_id` / `orders.user_id` → `users`; все подписки/отмены сходятся.
- Воронка монотонна: 80 000 → 65 739 → 29 641 → 6 584 → 928 sessions.
- `SUM(orders.amount)` = $25 194.11 совпадает с golden-числом case 07.
- Real-data выручка £17 743 429 совпадает с case 26 (£17.7M).
- repeat-rate 3.5% (896 buyers / 31 repeat) и 72.4% (real) воспроизводятся точно.
- `ab_variant` split 50.4% / 49.6% — SRM-безопасно.
- Покрытие по датам непрерывно 2024-01 → 2024-06 (синтетика) и 2009-12 → 2011-12 (реал).
